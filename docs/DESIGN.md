# Stock Social — Design Record

Name: **Stock Social**. Repo: `stock-social`.
Date: 2026-10-12. Status: **Phase 1 approved, scaffolded.**

This document was produced in four stages. Each stage has one owner who proposes, the other two
review against three tests — **feasibility**, **scalability**, and **maintainability under changing
technology** — and the owner resolves. Dissent that was overruled is kept, on purpose.

## Stage 1 — Market thesis & MVP proposal (owner: BL)

### 1.1 The problem, stated as evidence
- Retail trading content is dominated by **unverifiable claims**: P&L screenshots, cherry-picked wins,
  paid chat-group "signal" services with no audited record.
- There is evidence of demand for following other traders' moves: social and copy-trading platforms
  report millions of funded accounts and growing copy-trading activity, and apps that mirror publicly
  disclosed portfolios have built businesses on it. (Internal hypothesis: cite current primary sources
  before using any figure outside this document.)
- The social and copy-trading features we reviewed show verified results **only for trades placed on
  their own platform** (single-broker social features, exchange copy-trading). A trader with accounts at
  several brokers and a crypto exchange has no single, portable, verified record. **That gap is the
  wedge.**

### 1.2 Who it is for
**Supply (traders who publish) — the scarce side; win this first.**
- ICP-S1: "Signals seller." Sells a paid chat group, 1k–50k followers on social and video platforms,
  20–40 trades/mo in US equities/ETFs. Pain: buyers don't trust screenshots; churn is high. Job: *prove
  I'm real so more people pay me.*
- ICP-S2: "Proud hobbyist." 18–30, trades actively, already posts wins on short-video and photo apps.
  Job: *status.*

**Demand (people who watch) — abundant; capture through shared links.**
- ICP-D: 18–27, mobile-only, discovers finance through short video, attention span of one swipe.
  Job: *learn what real traders actually do, and be entertained by the outcome.*

### 1.3 Positioning
> **Verified trades, straight from the broker.**
> A trader's record is pulled read-only from their broker, can't be edited, and shows the losses too.

Against (by category): investor microblogs and social feeds (claims are unverified), charting-idea
communities (ideas, not trades), single-broker social and copy-trading features (one platform only),
forex-only performance trackers (one asset class).

### 1.4 Proposed MVP (BL's first ask)
1. Read-only broker connection → verified trade history
2. Public profile with stats and a shareable stat card
3. Vertical swipe feed of verified trades (a full-screen, short-video-style feed, for trades)
4. Trader writes a short thesis on each trade (UGC)
5. "Call it" swipe predictions with points
6. Weekly leagues
7. Creator subscriptions
8. Live "Earnings Night" rooms

### 1.5 Metrics BL proposed
- Traders connected (supply), shares per trader per week, profile views from external referrers,
  viewer D1/D7/D30.

## Stage 2 — Architecture & technical plan (owner: ENG)

### 2.1 Principles
1. **One deployable.** A single Next.js app (UI + server routes + cron endpoint). No microservices,
   no queue, no cache layer until a measured number demands one.
2. **Vendors live in exactly one file each.** `lib/broker.ts` is the only file that imports the
   SnapTrade SDK. When a vendor or paradigm changes, one file changes.
3. **Raw in, derived out.** Broker activities are stored raw and immutable. Everything displayed
   (closed trades, stats) is **derived and fully recomputable** from raw rows. A bug in P&L math is
   fixed by recomputing, never by migrating user-visible data.
4. **Plain SQL.** `db/schema.sql` + the `postgres` driver. No ORM: Postgres outlives every ORM, and
   agents read SQL fluently.
5. **Stdlib first.** Node's built-in test runner, `node:crypto` for secret encryption, native TS type
   stripping (Node ≥ 23.6) for scripts — no build step outside Next.

### 2.2 Stack
| Layer | Choice | Why | Exit cost if it changes |
|---|---|---|---|
| Runtime | Node 24 | Native TS, stable `node:test` | Low |
| Web | Next.js App Router, React, TypeScript | One framework for UI, API, OG images; largest hiring/agent pool | Medium — UI is plain React components |
| DB | Postgres 17 | Relational + JSONB for raw payloads; every host supports it | Very low |
| DB access | `postgres` (postgres.js) tagged-template SQL | Tiny, no codegen | Very low |
| Broker data | SnapTrade, read-only connections | Multi-broker, read-only scope | Contained to `lib/broker.ts`; raw payloads retained |
| Hosting | Any Node host (e.g. Vercel) + managed Postgres | Nothing host-specific in code; cron is a plain HTTP endpoint | Very low |
| Auth | Phase 1 dev stub (refuses to run in production); managed auth before public launch | Avoid building auth | Contained to `lib/session.ts` |

### 2.3 Data model (`db/schema.sql`)
- `users(id, handle unique, display_name, bio, is_adult_attested, snaptrade_user_id, snaptrade_secret_enc, created_at)`
  - `snaptrade_secret_enc` is AES-256-GCM encrypted with `APP_SECRET_KEY`; the plaintext is a
    credential and never touches logs or the client.
- `activities(id, user_id, source, external_id, account_id, symbol, side, units, price, fee, executed_at, raw jsonb, created_at)`
  - `unique(source, external_id)` → sync is idempotent; re-running never duplicates.
  - `source ∈ {snaptrade, demo}`. **Nothing user-typed ever lands here.**
- `closed_trades(id, user_id, account_id, symbol, opened_at, closed_at, return_pct, holding_days, thesis, thesis_status)`
  - Derived: deleted and rebuilt per user on every sync. `thesis` survives rebuilds because it's keyed
    by `(user_id, account_id, symbol, closed_at)` and re-attached.
  - Quantity and prices are deliberately **not** stored here — the display layer can't leak what it
    doesn't have.

### 2.4 Verification definition (the product's core promise)
A trade is **Verified** if and only if every activity it is derived from has `source = 'snaptrade'`.
`demo` data is labeled **Demo** in the UI everywhere it appears. There is no manual entry path.

### 2.5 Trade math (pure functions in `lib/trades.ts`, unit-tested)
- **Matching:** FIFO lots per `(account_id, symbol)`, long only in Phase 1.
- **One closed trade per sell activity.** A sell that consumes several buy lots produces one trade with
  the unit-weighted average entry.
- `return_pct = (exit_value − entry_cost − fees) / entry_cost`, fees from both legs prorated by units.
- **Unmatched sells are dropped**, not guessed: positions opened before the broker's history window
  have no verifiable entry. The profile shows "N earlier positions excluded (no entry on record)".
- **Stats:** trades, win rate, average return, average win, average loss, profit factor
  (Σ winning % / |Σ losing %|), median holding days, **max drawdown of an equal-weighted per-trade
  equity curve**. Labeled exactly that way in the UI — it is *not* account return, and we don't
  pretend it is.
- Account-level time-weighted return needs daily balance snapshots → Phase 2.

### 2.6 Feed ranking (one SQL query)
`score = ln(1 + |return_pct| × 100) × exp(−age_hours / 48)`, traders with ≥ 5 closed trades only.
Losses rank exactly as high as gains of the same size (`|return_pct|`) — the brand promise, enforced
in math. Personalization is Phase 2.

### 2.7 Sync
- `POST /api/sync` with `Authorization: Bearer $CRON_SECRET`, called hourly by the host's cron.
- Per connected user: fetch activities since the last `executed_at` − 7 days (brokers backfill late),
  upsert, rebuild that user's `closed_trades`.
- Sequential loop. Ceiling: ~5k traders/hour at ~0.5s each. Upgrade path: shard by `user_id % N`
  across N cron calls, then a real queue. Marked `ponytail:` in code.

### 2.8 AI plan (where AI earns its place, and where it doesn't)
| Use | Phase | Model tier | Notes |
|---|---|---|---|
| **Agentic development** — Claude Code with CLAUDE.md, hooks, worktrees | Now | Frontier | The highest-leverage AI in this company is the one writing the code |
| **Thesis moderation** (claims of guaranteed returns, pump language, solicitation, off-platform payment links) | Phase 1: rules; Phase 2: LLM classifier | Small/fast (e.g. Claude Haiku) with structured output | Fail closed: on API error, hold for review, never auto-publish |
| **Card captions** — one-line hook generated from verified numbers only | Phase 2 | Small/fast | Numbers come from the DB, never from the model; model writes words only |
| **Trader archetype** (plain descriptions such as "short-hold trader", "long-hold investor") | Phase 2 | Deterministic rules first | Rules from stats are explainable and free; an LLM adds nothing here |
| Trade recommendations / "AI picks" | **Never** | — | Personalized advice = adviser registration. Off-strategy. |

AI maintainability rule: **every model call goes through one module, takes typed input, returns a
schema-validated object, and has a 50-example eval file checked into the repo.** When models change
(they will, quarterly), swapping is a one-line model ID change plus re-running the eval.

- Hiding, deleting or editing individual trades; opting single accounts out of a connected login; deleting history on disconnect (TR-1, TR-2, TR-5).

- Rewards for trading **frequency**. Badges reward accuracy and risk-adjusted results only.
- Points convertible to money; real-money predictions; loot boxes; paid streak saves.
- Holding customer funds or placing trades.
- Personalized recommendations ("you should buy X").
- Hiding losses, or ranking gains above equal-sized losses.
- Manual or self-reported trades shown as Verified.

## Stage 5 — Product design spec (owner: human, added 2026-10-13)

Requirements set by the human. Every variant must meet them, and the Reviewer enforces each **Must**.
IDs (CH-, TR-, SW-) are cited in issues and PRs.

### 5.1 Charts

**CH-1 · Profile performance chart (total)**
- **Where:** profile, directly under the headline stats; also in the swipe-in profile pane (SW-1).
- **Plots:** cumulative return of the trader's verified closed trades, compounded with equal weight per
  trade, stepping at each close date, starting at 0% on the first trade. This is the series behind max
  drawdown (§2.5). When account-level returns exist (Phase 2 balance snapshots), switch to
  time-weighted account return and relabel.
- **Must:** the y-axis includes 0% and is never cropped to flatter the curve; drawdowns stay visible;
  the label states exactly what is plotted ("Return if every trade were the same size"); percent only,
  never dollars or position size; open positions are excluded and their unrealized result shown next
  to it (TR-4).
- **Look:** full width, ~160px tall on mobile; line in the neutral text color; area above 0% tinted with
  the up color, below 0% with the down color; a dot per closed trade; final value labeled at the right.
- **Accessible:** `role="img"` with a summary label ("312 trades, +41% total, max drawdown −18%");
  the trade list below is the data table.
- **Build:** server-rendered inline SVG from data already loaded; no chart library.
- **Share card:** the share image (§3.1 item 4) adds a small version of this curve.

**CH-2 · Per-trade chart**
- **Where:** each feed card, above the big return %; expandable from each row in the profile trade list.
- **Plots:** the symbol's daily close as % change from the entry day (entry = 0%), from 5 trading days
  before entry to 5 after exit; vertical markers at entry and exit; the held period highlighted.
- **Must:** y-axis in % from entry, never price or quantity; the exit marker sits at the trade's
  actual return.
- **Needs** daily price history, which is a new vendor: blocked on decision 5.4.1. Cache closes in a
  `daily_closes(symbol, day, close)` table behind one module, `lib/prices.ts`. Until decided, cards
  show no chart (no placeholder).

### 5.2 Trust: preventing cherry-picked records

"Verified" proves each trade is real. These rules make the **record as a whole** honest. Every
cherry-picking route and the rule that closes it:

| ID | How a trader could game it | Rule (Must) |
|---|---|---|
| TR-1 | Hide or delete individual losing trades | No per-trade hide, delete or edit, ever. Every trade from a connected account is published. Only the thesis is editable. |
| TR-2 | Connect only the "good" account under a broker login | Every account under a connected broker login is included. No per-account opt-out. |
| TR-3 | Start the record after a hot streak | Import the full history the broker provides, not just from the connect date. The profile shows "Record since ‹first trade date›". |
| TR-4 | Sell winners, hold losers forever, so realized stats look great | Show open positions next to realized stats, as prominent as the headline: "Open: 6 positions · −23% unrealized", in the down color when negative. Uses SnapTrade positions (average cost and current price), so no new vendor. |
| TR-5 | Disconnect after losses, or delete and start fresh | Disconnecting freezes the record: it stays public with "Disconnected ‹date›". Removing an account keeps its trades, marked "Account removed ‹date›". Only deleting the whole profile removes history, and that handle can't be reused for 1 year. |
| TR-6 | Attach the same broker account to a new profile to reset | A broker account can belong to only one profile, ever (unique on the broker's account ID). |
| TR-7 | Advertise a lucky short streak | Headline stats and the share card always show all-time numbers; 30d/90d views are secondary and labeled. Profiles under 30 days of history or 10 closed trades show a "New record" badge. |
| TR-8 | Trade elsewhere at an unconnected broker | Undetectable, so be explicit: the profile lists the connected brokers and number of accounts, and copy never claims "all of their trades". Phase 2 account-level returns remove within-account gaming entirely. |

**TR-9 · Confidence interval on performance**

A record is only as convincing as its sample. TR-9 shows how sure we can be, using the three things that
determine it: **returns** (size and spread), **frequency** (how many independent bets, over how long)
and **duration** (how long capital was tied up). Computed by one pure function, `confidence()` in
`lib/trades.ts`, from data already stored; no new vendor.

*Inputs per trade i:* log return `xᵢ = ln(1 + rᵢ)`; days held `dᵢ = max(holding_days, 1)`.
Open positions (TR-4) are included at their current unrealized return and days held so far, so
holding losers can't flatter the interval.

1. **Frequency → independent bets.** Trades in the same symbol whose holding periods overlap form one
   cluster (one bet). `K` = number of clusters. `span` = days from first entry to last exit (or today
   for open positions). Shown as "~15 trades/month over 61 days".
2. **Returns → per-trade interval.** `m = Σx / n`. Cluster-robust standard error
   `SEₘ = √(K/(K−1) · Σ_c (X_c − n_c·m)²) / n`, where `X_c` and `n_c` are each cluster's summed log
   return and trade count. 95% interval `m ± t(K−1)·SEₘ`, converted back with `eˣ − 1`.
3. **Duration → pace interval.** Return per day invested `R = Σx / Σd`, with
   `SE_R = √(K/(K−1) · Σ_c (X_c − R·D_c)²) / Σd` (`D_c` = cluster's summed days). Shown per 30 days
   invested: `e^{30R} − 1`, with the interval from `R ± t(K−1)·SE_R`. This stops a +2% trade held for a
   day and one held for a year from counting as the same result.
4. **Verdicts** (from the pace interval and the sample):

| Evidence | Rule | Edge | Rule |
|---|---|---|---|
| Too early | K < 10: no interval shown, "Too early to tell (K of 10 bets)" | Positive | pace interval entirely above 0 |
| Thin | K < 30 or span < 90 days | Negative | pace interval entirely below 0 |
| Moderate | K ≥ 30 and span ≥ 90 days | Unclear | interval includes 0 |
| Strong | K ≥ 100 and span ≥ 365 days | | |

- **Display (Must):** the headline average return always carries its range once K ≥ 10:
  "+1.3% per trade (−0.1% to +2.7%)", plus one line "Edge: unclear · Evidence: thin (30 bets, 60 days)".
  Pace and the method sit one tap deeper. Losses and negative edges are shown with the same prominence.
- **Copy (Must):** never "skill", "proven", "guaranteed" or similar; the label describes evidence, not
  the trader.
- **Ranking (Must):** any ranking of traders (lists, "top traders", future leaderboards) sorts by the
  pace interval's **lower bound**, never by raw averages, so small lucky samples can't top it.
- **Share card:** shows the evidence label next to the headline numbers.
- **Tests (Must):** unit tests for clustering of overlapping same-symbol trades, K < 10 → too early,
  a hand-computed example, and zero spread (no division by zero).
- **Known limits:** trades in different but correlated stocks (e.g. two chip makers in the same week)
  still count as separate bets, so intervals are somewhat optimistic for concentrated traders; fat-tailed
  returns make the t-interval optimistic too. Upgrade path: cluster by sector or week, or a cluster
  bootstrap. `t(K−1)` may use a standard approximation (accurate to ~0.01 for K ≥ 6).
- **Example (demo data):** Dan +0.9% (+0.4% to +1.3%) per trade, edge positive, evidence thin
  (30 bets, 61 days); Maya +1.3% (−0.1% to +2.7%), edge unclear; Yuki +0.4% (−3.4% to +4.3%), unclear.

### 5.3 Swipe to open a profile

**SW-1 · Swipe left on a feed card to open the trader's profile pane; swipe right to return**
- **Build:** each feed item becomes a horizontal scroll-snap row of two panes, [trade card | profile
  pane], inside the existing vertical scroll-snap feed. Native scrolling provides the gesture,
  momentum and direction locking; no gesture library.
- **Profile pane:** name, verified badge, headline stats, open positions (TR-4), the CH-1 chart, the
  last 5 trades, and "See full profile →" linking to `/u/[handle]`.
- **Must:** vertical swipes still move between trades; a horizontal swipe never also scrolls
  vertically; returning lands on the same card; tapping the name still opens the full profile; with
  keyboard focus on a card, → opens and ← closes the pane; `prefers-reduced-motion` snaps instantly.
- **First run:** the first card shows a subtle "Swipe ← for profile" hint once (remembered on the
  device), gone after the first swipe.
- **Reserved gesture:** left/right on the default feed means profile. A future "Call it" prediction
  mode (Phase 1.5 idea) must be a separate mode, not the default feed.
