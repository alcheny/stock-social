# F-10 feed record strip: load check (2026-11-01)

Plan §7 and round 3 R3-1: `stripEvidence` runs in `loadFeedPage` (via `feedStrips`, memoised per trader by row count and
newest id), so `LOAD=1 node --expose-gc --test lib/feed.load.test.ts` measures it. Budget: signed-out server time p95
under 400 ms. "Before" ran on the branch before any F-10 feed edit. "After" is the change: `records()` sends `opened_at`
as an 8th field in the profile's list order, and `page.strips` is built. All 6 load tests passed in every run. The
container is shared with another engineer's work, so expect ±20–40 ms run-to-run noise (two "after" samples are below).

| Case (feed server time p95, 60 pages) | Before | After, run 1 | After, run 2 |
|---|---|---|---|
| 500 traders, 12 heavy | 145 ms | 134 ms | 134 ms |
| 500 traders, 50 heavy (fix round 1) | 156 ms | 232 ms | 219 ms |
| Section on every page, 50 heavy: signed out | 180 ms | 312 ms | 234 ms |
| Section on every page, 50 heavy: signed in (budget 800 ms) | 194 ms | 268 ms | 244 ms |
| 50 heavy, 45 in one holding period | 193 ms | 237 ms | 258 ms |
| Page 2 with no kept list, 150k late activities (weights kept) | 268 ms | 214 ms | 198 ms |
| Page 2 with no kept list, 15 traders × 10k late closes (weights kept; the test asserts a cold median under 1 s) | 486 ms | 777 ms (one outlier; next highest 391) | 399 ms |

The case with 15 traders importing 10k late closes each was already over 400 ms before the change (p95 486 ms; that
test asserts the cold median, which it meets).

Every case stays inside its budget. On heavy pages the after numbers are about 40–60 ms higher. Where that comes from:
- Strip figures: a micro-benchmark of `feedStrips` over 30 traders (20 with 4,700 closes each) takes about 35 ms cold and
  about 1 ms warm. The load test repeats pages 1 to 3, so after the first pass the memo serves them.
- The 8th field: parsing about 94k rows with `opened_at` costs about 15–30 ms more than with 7 fields (micro-benchmark).
  This is most of the increase. It is marked as a ponytail in `lib/feed.ts#records1`.
- `order by closed_at desc, id desc` inside the aggregate: an A/B run on the section case gave 240/247 ms with it and
  249/233 ms without it, so its cost is within noise. It is kept because the strip then sums in the profile's order:
  the floats are the same, not just the printed text (lib/record-strip.db.test.ts, K equality).

Statement count (default DB test, lib/record-strip.db.test.ts): pages with ~10 and with ~30 traders issue the same
number of statements, and `records()` issues at most 2. The strip adds no statement.
